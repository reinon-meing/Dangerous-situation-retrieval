## 一、30 秒项目介绍（开场页文案）

> 灵御 TA2 双臂机器人，在「危境取物」赛题中完成 **红区抓取 → 黄区洗消 → 绿区交接** 的自主闭环。
> 我们在大赛提供的 **Intel 双卡 B70** 平台上，跑通了 **π0.5 端到端视觉-语言-动作模型** 的完整链路：
> 数据采集 → 硬件加速转换 → 云端训练 → 本地 XPU 推理 → 真机执行。
> 全链路现场实测：**解码 45 fps / 延迟 8.4 ms**，手臂执行精度 **0.003 弧度**。

## 二、赛题拆解

| 项 | 内容 |
|---|---|
| 赛题 | 危境取物（危险品应急处置）|
| 平台 | 灵御 TA2 双臂轮式机器人 |
| 官方算力 | Intel Xeon + 2× Intel Arc Pro B70 |
| 任务链 | 红区抓取 7 cm 沙包 → 黄区停留 10–15 s 洗消 → 绿区放置/交到人手 |
| 评分 | 完成度 60 + 技术方案 30 + 答辩 10 |

**我们的技术选择**：不用传统"感知-规划-控制"分模块，而是 **端到端 VLA**——输入图像+状态+语言，直接输出关节动作。

理由：
1. 赛题是"抓特定物体、按固定流程"的**结构化短程任务**，端到端比手写规划更省时间
2. 官方提供了 π0.5 训练/部署全套工具链（数据格式、转换镜像、推理镜像）
3. 我们只有 2 人 48 小时，端到端让我们能把精力放在**数据**上

## 五、核心技术点（PPT 建议每页一个）

### 1. 端到端 VLA 替代分模块

传统方案：YOLO 检测 → 手眼标定 → 逆运动学 → 轨迹规划。
我们：**图像 + 状态 + 语言 → 动作**，一条网络走完。

> 价值：把工程复杂度从"模块联调"转移到"数据质量"，48 小时内可交付。

### 2. 动作块（Action Chunk）与开环执行

模型一次输出 **30 步动作**，客户端只执行前 8~16 步就重新推理。

> 价值：把 45 Hz 控制环路里的推理耗时（8~280 ms）藏起来，动作依然连续。

### 3. 数据管线：MCAP → LeRobot

```
机器人录制（MCAP 2.8 GB / 27 min）
   → B70 的 rosbag2lerobot 镜像（VA-API 硬解 + 45 fps 对齐 + 三路相机切分）
   → LeRobot 数据集（76 维状态 + 16 维动作 + 3 路视频）
   → 上传 A100 训练
```

### 4. 训练迭代（真实数据）

| 版本 | 数据 | 条数 | 步数 | loss | 结果 |
|---|---|---|---|---|---|
| v1 | move_vaapi（含底盘 19 维）| 25 | 2125 | **爆炸到百万** | ❌ 常量维度炸归一化 |
| v2 | 同上（改 16 维）| 25 | 2125 | 0.0079 | ⚠️ 欠训练 |
| v3 | move_raised | 56 | 6036 | **0.0035** | ✅ 抓取可用 |
| v4 | move_all | 355 | 6857 | 0.0058 | ✅ 数据量 ×6 |
| **v5** | move_place | 86 | 6086 | **0.0034** | ✅ **放置到人手** |

### 5. 部署：JAX checkpoint → PyTorch → XPU

```
A100 上 42 GB checkpoint（params 12G + train_state 31G）
   → 只传 params + assets（12 GB，3 分钟）
   → B70 CPU 转换（15 分钟，811 tensors）
   → 6.8 GB model.safetensors
   → B70 GPU0 加载，显存 7.8 GB
```

## 六、小巧思（★ 最能拿分的部分）

### 巧思 1：用"离线仿真器"定位缺陷，全程不碰机器人

**问题**：实机上手臂乱走、所有关节顶到限位，怀疑模型/数据/部署各种可能，试一次要 5 分钟。

**做法**：在 A100 上写一个**离线推理器**——把训练数据集的某一帧（3 路图 + 状态 + prompt）直接喂给模型，和**录制的真实动作**对比。

**结果**：

| 检查 | 数字 |
|---|---|
| 单帧预测 vs 录制 | MAE **0.015 弧度** |
| 整条 episode 闭环（每 16 步重推理）| 左臂 0.005 / 右臂 **0.008 弧度** |
| 误差是否累积 | 否（chunk 末端仍 0.006）|

**价值**：**20 分钟定位问题，0 次机器人风险**。还顺带证明了模型质量。

> PPT 可以放一张图：左边"实机乱走"，右边"离线误差 0.3°"，形成对比。

### 巧思 2：靠"归一化统计的量级"一眼判断配置错没错

**问题**：训练端和推理端用了不同版本的 openpi 代码，一边 `use_delta_joint_actions=False`（绝对动作），一边 `True`（增量动作）。结果推理时**把当前关节角加了两次**：

```
下发值 ≈ 当前关节角 × 2  →  全部超出限位  →  手臂乱走
```

**判据（30 秒就能看出来）**：

| `norm_stats.actions.q01` 的量级 | 含义 |
|---|---|
| `0.4 ~ 1.5` | **绝对关节角**（正常）|
| `±0.1` | 增量动作（若训练用的是绝对，就是配置错）|

**佐证**：实机日志 `l_joint2 = 2.746 ≈ 2 × 1.361`、`r_joint7 = -1.300 ≈ 2 × (-0.652)`。

**修复**：3 行补丁把推理端改成绝对动作 + 恢复原始统计，重启 server。

> 这条特别适合做"技术深度"页：**一个数字就能定位根因**。

### 巧思 3：识别出"左臂是假数据"

**问题**：放置模型在实机上，左臂总是大幅摆动，但人看着"左臂不该动"。

**查数据发现**：

| 对比 | 左臂 | 右臂 |
|---|---|---|
| `action[t]` vs `state[t+1]` | **0.233 弧度** ❌ | 0.0196 ✅ |
| 30 帧内实际位移 | **0.0001 弧度**（完全静止）| 正常运动 |

**结论**：录制时**左臂没有跟随指令**（指令让它去 A，实际停在 B），模型学到的左臂目标是"从未实现过的姿态"。

**处理**：客户端加一个补丁，**冻结左臂**（忽略模型输出的左臂 7 维，固定为起点姿态），只让右臂执行。

> 这个"数据里藏着假目标"的发现，是很硬的技术点。

### 巧思 4：双 server 并行，避免中途切换

抓取模型和放置模型是两个 checkpoint。常规做法是中途重启 server（60~90 秒，手臂要一直保持）。

**我们的做法**：**同时起两个 server**，监听 8000（抓取）和 8001（放置），客户端按 `--remote-port` 选。

```
抓取阶段: main.py --remote-port 8000 --prompt "pick sandbag"
放置阶段: main.py --remote-port 8001 --prompt "place sandbag"
```

> 显存代价只有 7.8 GB（单卡 24 GB，两个共 15.6 GB）。**切换零等待**。

### 巧思 5：定时停止 + 姿态保持（因为 Ctrl-C 杀不掉）

**踩过的坑**：

| 做法 | 结果 |
|---|---|
| 终端按 `Ctrl-C` | ❌ 只杀了 `docker exec` 客户端，容器里 `main.py` 继续跑 |
| `python ... &` + `kill -INT $!` | ❌ 非交互 bash 的后台进程**自动忽略 SIGINT** |
| **`timeout -s INT 30 python ...`（前台）** | ✅ 到点自动优雅停止 |

**配套**：`hold_now.py` 在停止后持续发布当前姿态 + 夹爪力，把手臂**锁住不动**（防止停掉后手臂下沉、夹爪松脱）。

### 巧思 6：手势启动门控

`b-run.sh` 里加了**张开手掌手势**才启动的开关（`gesture_gate.py`）：
启动前先确认人手在画面里、且不占用 UDP 8890，然后才允许跑模型。

> 价值：**避免误触发**，现场演示更安全；也算一个"人机协同"的小设计。

### 巧思 7：限位与坐标的定量分析

实机发现右臂 j4（肘）只能到 `[-2.2, -0.25]`，而训练数据是 `+0.22~+1.77`，一度以为硬件坏了。

**用数据定量分析后确认**：
- 左右臂"镜像安装"，右臂肘合法范围本来就是负的
- 训练数据的 `+0.78` 换算到实机就是 `-0.78`，**完全可达**
- 之前的"卡死"其实是**取数时把 `state[7]`（左夹爪）当成了右臂 j1**，整体错位一格

> 这个"按位查数据"的过程，说明我们有能力**用数据验证硬件假设**，而不是靠猜。

### 巧思 8：转换用 VA-API，把 30 分钟压到 35 秒

| 环境 | 25 条 episode | 画质 |
|---|---|---|
| VMware + CPU（libx265）| ~30 分钟 | 被迫降到 480×240 |
| **B70 + VA-API 双卡** | **35.5 秒** | **960×480 全画质** |

**≈ 50 倍加速**，而且画质更好（更高分辨率对 VLA 的图像输入很关键）。

## 九、答辩预判问答

**Q1：为什么用端到端，不做模块化？**
> 任务结构化、动作短程；官方工具链完整；2 人 48 小时，端到端让我们把时间花在数据上而不是模块联调。而且端到端对"没见过的小扰动"（沙包位置变化）通常比手写规则更鲁棒。

**Q2：数据量够吗？会不会过拟合？**
> 抓取 56 条时 loss 在 4500 步后平台化，说明数据容量到顶；我们把数据扩到 355 条重训（v4），并保留 v3 做对照。放置单独训练 86 条。

**Q3：推理延迟多少？能实时吗？**
> 解码 8.4 ms、推理 0.28 s（热缓存）。通过动作块（一次出 30 步、执行 8~16 步）把推理藏进动作执行里，视觉上仍然是连续 200 Hz 指令流。

**Q4：怎么保证安全？**
> ① 关节指令在客户端按 `arm_config.yml` 限位夹取 ② FSM 心跳 1 秒超时自动暂停 ③ 动作块执行有速率限制 ④ 停用 `docker stop`，只用 SIGINT 优雅停（会先发零速度指令）。

**Q5：只用一个模型行不行？**
> 抓取和放置的数据起点不同（放置起点要求"手里已经夹着沙包"），所以现在是两段式。下一步是把两段录成一条完整 episode，训一个端到端模型。

**Q6：Intel 卡怎么跑 PyTorch 的？**
> 官方镜像 `openpi-xpu-env` 预置了 `torch 2.12+xpu` 和 XPU 版算子；`torch.xpu.device_count()=2`，两个 server 分别占一张卡/共享一张，显存 7.8 GB。

**Q7：数据转换为什么快 50 倍？**
> 用 Intel 的 VA-API 硬件编解码（`vah265dec` + `libvapp`）替代 CPU 软编，25 条 episode 从 30 分钟压到 35.5 秒，且保住了 960×480 全画质。

**Q8：怎么知道模型"学会了"而不是"记住了"？**
> ① 离线闭环测试：模型对训练集都能复现（0.005~0.008 弧度）② 实机换沙包位置测试 ③ 观察 loss 曲线是否平台化（说明容量到顶）。

**Q9：如果现场网络抖动？**
> 视频丢了模型会报 `dead sensors` 并**主动停止**（不会盲动）；关节状态有 1 秒超时保护。
