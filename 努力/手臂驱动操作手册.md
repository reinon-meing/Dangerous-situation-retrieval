# TA2 手臂驱动操作手册（验证版）

> 记录时间：2026-11-14 20:50
> 环境：B70 `OTII-E-2` (192.168.31.128) + 灵御 TA2 机器人 (192.168.31.217)

---

## 一、核心机制：FSM 心跳是唯一开关

**这是整晚踩的最大坑，也是最重要的一条。**

机器人有安全设计：

> `/api/fsm/enable` 如果 **1 秒内**没收到 `data=1.0`，机械臂**自动暂停**。

| fsm_state | 手臂状态 |
|---|---|
| **1** | 使能，会执行指令 |
| **0** | 失能，**无论发什么指令都不动** |

### 三条铁律

1. **心跳必须持续发**，频率 ≥ 1 Hz（实测用 20 Hz）
2. **心跳必须和策略同生共死**——同一个 shell 里后台运行
3. **每次启动策略前必须验证 `fsm_state == 1`**

### 血的教训

第一次跑 `main.py` 时，心跳在**另一个终端**发的。中途那个进程死了 → `fsm_state` 掉回 0 → 手臂完全不动。

**当时的表现极具误导性**：
- 模型正常输出（日志有 `First des_q command published`）
- 指令正常下发（`/can3/motor_cmd` 50 Hz）
- **但电机纹丝不动**

看起来像"模型不会用"，实际上是"手臂被安全机制锁住了"。

## 二、一次性前提（做完就固定，不用每次改）

### 机器人侧（System Config）

| 项 | 值 |
|---|---|
| Run mode | **API**（`meta_mode: 1`） |
| 左臂 / 右臂 | **启用** |
| 左臂 / 右臂控制模式 | **关节 joint**（`control_mode: 1`，不是 0=末端） |
| 底盘 | 启用（但 16 维模型不控制它） |
| 碰撞检测 | 开着（多一层保护） |

**操作顺序**：改完 → `Save config` → `Apply` → **物理重启机器人**

### 视频推流

机器人推流 APP → 目标 IP **`192.168.31.128`**（B70）→ UDP **8890** → 启动推流

### B70 侧

- client 容器已 `start`（带 `RENDER=/dev/dri/renderD129`、`ZENOH_ENDPOINT=tcp/192.168.31.217:9000`）
- server 已在 `127.0.0.1:8000` 运行

## 三、启动策略的完整命令

```bash
cd /root/USB/deploy
export OPENPI_DIR=$(pwd)/client/openpi

client/run_client.sh exec bash -c '
# ① 后台心跳（关键：和 main.py 在同一个 shell）
ros2 topic pub -r 20 /api/fsm/enable std_msgs/msg/Float32 "{data: 1.0}" >/dev/null 2>&1 &
HB=$!
sleep 1

# ② 复位（每次都做，让手臂到已知姿态）
python examples/teleavatar_v2/zero.py

# ③ 跑策略
python examples/teleavatar_v2/main.py \
  --remote-host 127.0.0.1 --remote-port 8000 \
  --video-decode va --prompt "pick sandbag"

# ④ 清理
kill $HB 2>/dev/null
'
```

`main.py` 运行参数说明：

| 参数 | 值 | 说明 |
|---|---|---|
| `--remote-host/port` | `127.0.0.1:8000` | server 地址 |
| `--video-decode` | `va` | VA-API 硬解（必须，B70 用 renderD129） |
| `--prompt` | `pick sandbag` | **必须和训练的 `--task` 一字不差** |
| `--enable-chassis` | **不加** | 16 维模型不含底盘，加了会报错 |
| `--rtc` | **不加** | 服务端没开 RTC |

## 五、手臂能不能动——30 秒自检（最有用的一条）

**不启动模型，直接手动发一个目标位姿，验证整条执行链路。**

```bash
client/run_client.sh exec bash -c '
ros2 topic pub -r 20 /api/fsm/enable std_msgs/msg/Float32 "{data: 1.0}" >/dev/null 2>&1 &
HB=$!
sleep 1

b=$(timeout 2 ros2 topic echo --once /left_arm/joint_states --field position 2>/dev/null | grep -o "array.*")
echo "BEFORE: $b"

ros2 topic pub -r 20 /api/left_arm/joint_cmd sensor_msgs/msg/JointState \
  "{position: [0.70, 1.60, -0.90, 1.10, 0.50, -0.40, 0.60]}" >/dev/null 2>&1 &
PUB=$!
sleep 5
kill $PUB 2>/dev/null

a=$(timeout 2 ros2 topic echo --once /left_arm/joint_states --field position 2>/dev/null | grep -o "array.*")
echo "AFTER : $a"

kill $HB 2>/dev/null
'
```

| BEFORE vs AFTER | 结论 |
|---|---|
| **数字变化** | ✅ 链路、电机、FSM 全部正常 → 问题在模型 |
| **数字相同** | ❌ 执行链路有问题 → 查 FSM/急停/模式 |

**这是区分"模型问题"和"硬件问题"最快的方法，务必先跑这条。**

## 六、完整信号链路（用于排查）

```
server:8000  ──(websocket, 动作块)──  main.py
                                        │
                                        ├─ /api/left_arm/joint_cmd   ← client 发布
                                        │
                                     MUX（模式路由）
                                        │
                                        ├─ /left_arm/joint_cmd       ← MUX 输出
                                        │
                                    CAN 桥（robstride bridge）
                                        │
                                        ├─ /can3/motor_cmd  50 Hz    ← 4 个关节
                                        ├─ /can4/motor_cmd  50 Hz    ← 3 关节 + 夹爪
                                        │
                                      电机
                                        │
                                        └─ /can*/motor_states 200 Hz ← 反馈
```

**CAN 总线与关节的对应关系（实测）：**

| CAN | 内容 |
|---|---|
| can3 + can4 | **左臂**（7 关节 + 夹爪） |
| can0 + can1 | **右臂**（7 关节 + 夹爪） |
| can2 | 底盘（3 轮） |

排查时逐段确认：
1. `/api/left_arm/joint_cmd` 有没有消息（client 在发吗）
2. `/left_arm/joint_cmd` 是否跟随（MUX 在转发吗）
3. `/can3/motor_cmd` 是否跟随（CAN 桥在工作吗）
4. `/can3/motor_states` 是否跟随（**电机执行了吗**）

## 七、安全规则（手册与 README 明确要求）

| 规则 | 说明 |
|---|---|
| **Ctrl-C 停止** | 发 SIGINT，先发零速度再退出 |
| **严禁 `docker stop / kill / rm -f`** | 跳过零速度指令，底盘会继续动约 1 秒 |
| **SSH 断连不会停机** | 机器人会继续运动！断网先拍急停 |
| **首次运行必须专人守急停** | 模型行为不可预测 |
| **16 维模型底盘不动** | 不发底盘指令，不会有"冲出去"风险 |

安全停止：

```bash
# 正常停止
Ctrl-C
# 或
client/run_client.sh exec pkill -INT -f examples/teleavatar_v2/main.py
# 或
client/run_client.sh stop
```

## 八、常见问题对照

| 现象 | 原因 | 修法 |
|---|---|---|
| 手臂完全不动，模型日志正常 | **FSM 心跳断了** | 确认心跳和 main.py 同一 shell |
| `fsm_state: 0` | 1 秒没收到心跳 | 重启心跳 |
| 关节指令顶到限位（如 j2 1.900） | 模型输出超限 | 训练数据的姿态分布问题 |
| `Observation unavailable — dead sensors` | 视频某几路 1 秒没新帧 | 查推流/线缆；重试 |
| `Failed to find a free participant index` | ROS 节点开太多 | 重启 client 容器；一次 exec 查多项 |
| `error_code` 类型无效 | 容器缺 `robstride_actuator_bridge` 包 | 跳过，用 CAN 话题间接判断 |
| `/left_arm/fsm_state` 无消息 | 手臂级 FSM 话题不常发 | 以 `/fsm_state` 为准 |
